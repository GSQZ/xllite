# 平台契约核实结论

更新：2026-10-23。记录四项在需求里点名要求核实的能力，各自的平台边界、当前实现状态与判定依据。**未实现的不写成已实现**；缺少合法观测手段的，不补猜出来的实现。

先给状态总览，避免把"已定论不做"误读成"还没做"：

| 能力 | 状态 | 缺什么 |
| --- | --- | --- |
| 找回密码 | 已实现 | 无 |
| 支付成功浮层 | **已定论不做** | 需要服务端订单状态查询接口，不是实现工作 |
| 小艺意图 | 契约已核实，代码未接入 | 需先确认接入条件，见 `XIAOYI-INTENT-INTEGRATION.md` |
| 实况窗 | 已接入，行为回归通过 | 真机显示与 TIMER 场景权益，属环境与审批 |

## 1. 找回密码

**结论：不做应用内重置流程，改为告知用户到学校平台处理。已实现。**

判定依据：

- 密码由学校统一身份认证平台（CAS）管理，应用侧没有修改凭据的接口。公开契约中不存在「重置密码」端点。
- 应用不做密码保存——`AuthManager` 不存密码，`callFeature` 系列签名里也没有密码参数（早期曾挂一个恒返回空串的形参，已删除）。因此应用既没有能力、也没有必要代用户改密码。
- 找回密码页面（`LoginPage` 的 `handleForgot`）只做本地状态切换：清空输入、展示说明，**不发任何网络请求**。页面文案直接指向学校信息服务部门。

这样处理避免了两种错误：假造一个"发送重置邮件"的按钮（背后没有接口），或跳转到不可控的外部网页冒充应用内能力。

## 2. 支付成功

**结论：应用侧不存在合法的支付结果观测手段，因此不实现支付成功浮层。保留设计稿，不落代码。**

判定依据：

- SDK 没有系统支付接口，充值为 `tradeType: 'WAP'` 的 WebView 支付，支付过程在网关侧页面完成。
- `partnerJourno` 字段只证明**订单对象返回**，不证明**支付成功**。
- 不存在订单状态查询接口，应用无法在回到前台后确认结果。

三种看似可行的替代方案都已被否掉：

| 方案 | 为什么不行 |
| --- | --- |
| 定时器延时后弹"支付成功" | 无论用户是否付款都会弹，是伪造 |
| 从支付页返回即视为成功 | 用户可能中途取消或失败返回，同样伪造成 |
| 依据 `partnerJourno` 判定 | 它只说明订单创建成功，下单不等于支付成功 |

当前实现的处理方式按网关返回分三种，都不宣称支付成功：

| 场景 | 应用行为 |
| --- | --- |
| 电费充值（`ElectricityPage`） | 提交后提示"支付请求已提交，请到一卡通账户核对到账结果"，判断权交回用户 |
| 充值下单缺支付入口（`RechargePage`） | 提示"订单已创建，但响应缺少支付入口字段，请到一卡通账户查询后再决定是否重试"，避免用户重复下单 |
| 充值下单有支付入口 | 进入 WebView 支付页，返回后不追加任何成功判定 |

`docs/previews/payment-feedback.html` 保留动效设计稿，供后续接入真实订单状态查询时使用。

**这一项与另外三项的区别**：实况窗、设备提醒卡片是"已实现、待设备验收"，等环境就绪就能补测；支付确认浮层是**已定论不做**——除非将来服务端提供订单状态查询接口，否则无论换什么实现方式都只能靠猜，而以猜测为基础的"成功"提示比不提示更有害。它不构成待完成事项。

代码现状可核：全仓库没有任何支付结果浮层的实现，现有的三处弹层是 `CampusSettingsPage` 的添加卡片菜单（`bindMenu`）与 `ScheduleTab` 的两处课程详情对话框（`showDialog`），都与支付无关。

## 3. 小艺意图

**结论：契约已核实，可落地目标只有一个；代码尚未接入。**

判定依据：

- `@ohos.app.ability.InsightIntentDecorator` 装饰器 @since 20 可用。
- 标准意图清单共 101 项，其中**没有**创建待办、创建提醒或写入内容的意图。
- `JumpFunctionPage` 只能打开指定页面，不能携带内容填充。

因此唯一可落地的目标是「打开课表页」。想把"新增待办"做成小艺意图（"提醒我明天交作业"）在当前平台清单里没有对应项，只能靠第三方模型聊天页冒名，那是产品假冒，不做。

接入前还需落实的事项见 `XIAOYI-INTENT-INTEGRATION.md`。

## 4. 实况窗（LiveView）

**结论：已接入并通过编译期与行为回归；真机验收未完成。**

判定依据：

- 使用 HMS `@kit.LiveViewKit`（@since 4.1.0(11)），位于 SDK 闭源 `hms` 层，不是 OpenHarmony 系统 API。
- 以 `TIMER` 场景承载课前倒计时与待办计时，胶囊、锁屏与通知中心三处呈现。
- 能力按字段各自引入的版本下发，不按特性整体开关：

| 成员 | 起始版本 | 低版本处理 |
| --- | --- | --- |
| `capsule.icon` | 4.1.0(11) | 不下发 |
| `primary.content` 的 `${placeholder.timer}` | 5.0.0(12) | 不下发 |
| `timer` | 5.0.0(12) | 不下发 |
| `capsule.isContentDisplayed` | 5.0.3(15) | 不下发 |
| `capsule.tailIcon` / `isTailIconDisplayed` | 6.0.0(20) | 不下发 |
| `primary.aliveTime` | 6.1.1(24) | 不下发 |
| `lifeCycleMode` | 26.0.0 | 不下发 |

- 版本号在载荷回滚时同步回滚。系统要求更新与结束的新版本号必须大于当前值，而被拒绝的调用不推进系统侧版本；本地计数若继续自增会跳过版本并触发序列冲突 `1003500011`，实况窗自此无法更新。
- 错误码已映射为可执行提示：`1003500005` 指向 TIMER 场景权限未获批，`1003500004` 指向系统开关未允许，`801` / `1003500003` 指向设备不支持或服务不可达。

**未完成的部分**：真机上的实况窗显示与提醒触发尚未验收。TIMER 场景权限申请编号 `1003500005` 未获批，`LifeCycleMode`（@since 26）与 `aliveTime`（@since 24）在 API 23 设备上不可控，这属于平台边界而非实现缺陷。申请材料见 `LIVEVIEW-APPLICATION.md`。
